# place-link 제품 요구사항 정본 (Product Baseline) v1.0

## 1. 문서 위상

이 문서는 place-link가 **"무엇을 만드는가"** 에 대한 단일 기준이다.

- 기술 결정("어떻게")은 [place-link_architecture_baseline.md](place-link_architecture_baseline.md), 개발 규칙은 [place-link_development_guide.md](place-link_development_guide.md)를 따른다.
- 본 문서는 `docs/legacy/`의 기획 문서 4종에서 **유효한 기획만 추출·정리**한 것이다. legacy 문서와 충돌하면 본 문서가 우선한다.
- 제품 결정의 변경(기능 추가/제외, 우선순위 변경)은 본 문서를 갱신하고, 구조에 영향을 주면 ADR을 동반한다.

## 2. 서비스 정의

- **한 줄 정의**: 커플이 직접 만든 데이트 코스를 등록·공유하는 UGC 큐레이션 플랫폼.
- **킬러 콘텐츠**: 유저(커플)가 등록한 실제 데이트 코스 데이터.
- **핵심 차별화**: 코스에 **"지훈❤️민지 코스"** 형태의 커플 명칭을 부여하고 명예의 전당으로 노출 — 소유욕·과시욕을 동기부여 장치로 사용.
- **해결하는 문제**:
  1. 분산된 정보(블로그, 릴스)로 인한 데이트 기획 피로
  2. 광고성 정보 불신 → 실경험 기반 신뢰
  3. 맛집/카페 위주를 넘어 팝업·전시·공방 등 트렌디한 경험 큐레이션

## 3. 타겟

| 세그먼트 | 설명                           | 핵심 가치                                                     |
| -------- | ------------------------------ | ------------------------------------------------------------- |
| 국내     | 특별한 데이트를 원하는 MZ 커플 | 초개인화·초효율 코스                                          |
| 글로벌   | 방한 외국인 관광객             | 한국 커플의 '찐' 로컬 데이트를 그대로 따라 하는 K-로컬 바이브 |

- 글로벌은 후순위가 아니라 **Day 1 요건**: ko/en 라우팅, 번역 파이프라인, 투트랙 지도(내국인 카카오/네이버, 외국인 구글) 딥링크.
- 초기 타겟 상권 (마이크로 타겟팅 후 확장):
  - 트렌드 세터형: 성수 / 신용산
  - 로컬 감성형: 서촌 / 북촌 / 한남
  - 서브컬처형: 홍대 / 연남 / 망원 / 을지로
  - 액티비티형: 잠실 / 여의도

## 4. 플랫폼 원칙

- **모바일 웹 우선.** 네이티브 앱은 푸시·백그라운드 위치·인앱 결제가 필수화되기 전까지 만들지 않는다.
  - 근거: 링크 클릭만으로 유입(바이럴·관광객), 카카오톡/SNS 공유 최적화, SEO 오가닉 유입.
- 공유 시 시각적 임팩트(OG 이미지)가 핵심 성장 루프이므로 코스 상세 페이지의 SSR·메타태그 품질은 기능이 아니라 성장 요건으로 취급한다.

## 5. 콜드 스타트 전략

사용자 데이터가 없는 초기 단계의 운영 전략:

1. **앵커(Anchor) 중심 반자동 코스**: 이번 주 핫한 팝업/전시/행사를 앵커로 지정하고, 주변 장소를 조합한 초기 코스를 제공.
2. **공공데이터 80%**: TourAPI, 서울열린데이터광장 등에서 기본 정보 수급 후 트렌디한 톤으로 가공.
3. **에디터 큐레이션 20%**: 공공데이터에 없는 최신 팝업을 내부 에디터(가상 커플 페르소나)가 수동 등록해 초기 톤앤매너 설정.
4. **빈칸 채우기 넛지**: 앵커 주변의 빈 동선을 유저가 채우도록 유도해 UGC 획득.

→ 이 전략이 요구하는 시스템: 앵커 지정 기능(admin), 외부 데이터 수집 파이프라인, 에디터용 장소/코스 수동 등록. 아키텍처 baseline 3단계(운영 기반)에 대응.

### 5.1. 데이터 소스 정의 (3원 체계)

플랫폼의 장소·코스 데이터는 세 가지 소스로 유입되며, 소스별로 신뢰·검수 정책이 다르다.

| 소스                 | 내용                                                                     | 검수 정책                 | 시기                                                                         |
| -------------------- | ------------------------------------------------------------------------ | ------------------------- | ---------------------------------------------------------------------------- |
| **공공데이터**       | TourAPI, 서울열린데이터광장 등 문화행사·관광지 정보. 자동 수집 + 톤 가공 | 자동 신뢰, 형식 정규화만  | 초기 주력 (80%)                                                              |
| **기업/행사 데이터** | 브랜드 팝업스토어, 전시, 플래그십 행사 정보                              | 홍보성·정확성 에디터 검수 | 초기: 에디터 수동 등록 → 파트너 포털(백로그) 가동 시 기업 직접 입력으로 전환 |
| **UGC (개인)**       | 커플이 등록한 데이트 코스 + 꿀팁                                         | 모더레이션 큐 (7.2)       | 킬러 콘텐츠. 성장할수록 비중 확대                                            |

- 세 소스가 같은 장소를 중복 생성할 수 있으므로 중복 병합(7.2 POI 관리)은 소스 간 병합을 전제로 설계한다.
- 모든 데이터는 출처가 기록되어야 한다 (가이드 INT-7). 출처는 향후 신뢰도 표시("공식 정보" vs "유저 제보")와 파트너 정산의 근거가 된다.
- 출처와 콘텐츠 종류는 별도 축으로 관리한다. 장소·행사·코스는
  `PUBLIC_API | BUSINESS | EDITOR | UGC` 출처를 가지며, 장소 종류(카페·영화관·박물관
  등), 행사 종류(전시·팝업·공연·상영 등), 운영 주체(공공·민간·비영리)는 각각
  독립된 관리형 값으로 저장한다. 공공 API에 실린 민간 행사를 공공 운영으로 추정하지
  않는다.

### 5.2. 행사성 데이터의 수명과 기간 표시

- 팝업·전시·행사는 상설 장소와 달리 **유효 기간을 가진 데이터**로 취급한다 (시작일/종료일 필수 — 기간 없는 행사 데이터는 등록 불가).
- **기간은 유저에게 항상 명시적으로 표시한다**: 행사가 노출되는 모든 화면(앵커 배너, 지도 마커/바텀 시트, 코스 상세 타임라인, 검색 결과)에 기간을 표기한다.
  - 표기 형식: 진행 중 → "~7.31까지" + 종료 임박(7일 이내) 시 "종료 D-5" 강조 뱃지, 시작 전 → "8.1 오픈", 종료 → "종료된 팝업" 딤 처리.
- 종료 시 자동 처리: 앵커에서 해제, 신규 코스에 추가 불가, 기존 코스 상세에는 "종료된 팝업" 표시 (코스 자체는 기록으로 유지).
- "스크랩한 팝업 종료 임박 알림"은 단계 4(성장 기능)의 알림에 포함한다.

### 5.3. 일정·운영시간 데이터

- 장소에는 정규 요일별 운영시간과 날짜별 임시 휴무·변경 시간을 분리해 저장한다.
- 영화·공연·체험처럼 회차가 있는 콘텐츠는 행사 전체 기간과 개별 회차를 분리한다.
- 모든 외부 일정은 공식 링크와 마지막 확인 시각을 보존한다. 구조화가 어렵거나 신뢰도가
  낮은 경우 시간을 추측하지 않고 공식 일정 확인 링크를 제공한다.
- 일정 데이터는 공공 API 자동 수집, 기업·기관 공식 링크, 에디터 검수, 사용자 오류 제보를
  함께 사용해 지속적으로 갱신한다.
- 오래되거나 수집에 실패한 정보는 최신 정보처럼 노출하지 않고 확인 필요 상태로 처리한다.

## 6. 보상 정책

- **Phase 1 (오픈)**: 금전 보상 없음. 명예의 전당 노출 + 뱃지 (과시 동기).
- **Phase 2 (활성화 후)**: 코스 트래픽 기반 제휴처 쿠폰, 스크랩 랭커 기프티콘. 멱등키·감사로그 등 기술 전제는 가이드 INT-3/AGT-4에 이미 반영됨.

## 7. 기능 명세 (구현 단계 매핑)

기능의 "무엇"을 정의한다. 각 기능은 아키텍처 baseline 7장의 단계와 매핑되며, 상세 UX 레퍼런스가 필요하면 legacy 문서를 참고하되 충돌 시 본 문서 기준.

### 7.1. 단계 2 — 핵심 사용자 경험

**홈**

- 동적 히어로: 접속 시간대·날씨 기반 개인화 카피 (예: 비 오는 저녁 → 실내 데이트 제안)
- 앵커 배너: admin이 지정한 핫플 캐러셀. 행사(팝업/전시)는 기간 표기 필수 (5.2). 클릭 시 해당 앵커가 채워진 코스 마법사로 이동
- 실시간 피드: 최신 UGC 코스 무한 스크롤. 카드 = 썸네일 + "OO❤️OO 코스" + 소요 시간 + 태그
- 필터: 상황별(기념일, 비오는 날)·예산별·분위기별 (바텀 시트)

**코스 생성 마법사 (3 Step)**

- Step 1 앵커 선택: 검색 + 핫플 리스트에서 메인 장소 1개
- Step 2 동선 메이커: 1–3일 일정과 일별 시작·종료 시간(최소 3시간)을 먼저 정하고, 앵커 반경 1–2km POI를 지도 마커로 표시 → 날짜별 [코스에 추가] → 드래그앤드롭 순서 변경 → 장소별 체류 시간과 50자 꿀팁 입력. 하루 최대 8곳·전체 최대 24곳이며 노드 간 거리·이동 시간을 표시한다. 앵커는 1일차 첫 장소로 고정한다.
- Step 3 발행: 선택한 모든 날짜에 장소가 1곳 이상이고 전체 장소가 2곳 이상일 때, 커플명 자동 네이밍("지훈❤️민지 코스"), 대표 이미지 지정, 날짜별 일정과 공유용 카드 미리보기 후 발행

**코스 상세 (공유 랜딩)**

- 트로피 헤더: 커플명 대형 타이포그래피, 명예의 전당 코스는 특별 연출
- 타임라인: 날짜별 세로 진행형, 노드별 도착·체류 시간 + 장소 정보 + 꿀팁 + 구간 거리/시간
- 투트랙 지도 버튼: locale 기반 카카오/네이버 ↔ 구글 지도 딥링크
- 액션 바: 스크랩, 카카오톡/링크 공유. OG 메타태그 SSR 생성
- 언어: `Accept-Language`/locale 기반 번역본 제공 (번역 상태 모델은 아키텍처 baseline 5장)

**마이페이지**

- 커플 연결(초대 링크/수락)·해제 + D-Day, 내가 만든 코스, 스크랩 목록 — 연결·해제·솔로 정책은 10장을 따른다

**명예의 전당**

- 주간/월간 스크랩 랭킹 + 에디터 수동 큐레이션 (운영 API로 제어)

### 7.2. 단계 3 — 운영·에이전트 기반

- 대시보드: DAU/MAU, 신규 코스 수, 스크랩 Top 10, 국가별 트래픽
- POI 관리: 장소 검색/수정/수동 등록, 앵커 지정, 중복 장소 병합(승인 게이트 대상)
- UGC 모더레이션: 욕설/광고 필터 큐, 블라인드 처리, 신고 접수·처리
- 번역 검수: 기계번역 결과 검토·오버라이드 큐
- 회원 관리: 유저 목록, 제재(Ban — 승인 게이트 대상)
- 명예의 전당/메인 배너 큐레이션
- **모든 운영 기능은 에이전트가 호출 가능한 API로 먼저 구현** (가이드 ARCH-6/AGT)

### 7.3. 단계 4 — 성장 기능

- 팔로우(워너비 커플), 댓글("이 코스대로 다녀왔어요" 포토 후기), 리액션 이모지
- 알림 (팔로우한 커플의 새 코스 등)
- 업적/뱃지 게이미피케이션 (칭호: '성수동 앰배서더' 등)
- 쿠폰/캠페인 (Phase 2 보상 정책 가동)

### 7.4. 단계 5+ — 백로그 (착수 시 ADR 필수)

**개인화 코스 추천(취향·행동 패턴 기반 For You 피드)**, AI 프롬프트 코스 생성, 데이트 가계부, 커뮤니티 Q&A, 인앱 예약/결제, 파트너(B2B) 포털, 커플 동시 편집, AR 네비게이션, 라이브 히트맵.
→ 유저 검증 전에는 설계·구현하지 않는다.

### 7.5. 데이터 자산 전략 — 추천의 원료는 지금부터 쌓는다

개인화 추천은 백로그지만, **그 원료가 되는 데이터 수집은 단계 2부터 시작**한다. 축적 없이는 단계 5에서 추천을 만들 수 없다.

1. **행동 이벤트**: 코스 조회/스크랩/공유, 필터 사용, 마법사 단계 진입·이탈, 지도 탐색 지역 등 핵심 행동을 표준 이벤트로 기록한다 (가이드 ANL 규칙).
2. **관리형 태그 사전**: 장소·코스의 분위기/예산/상황 태그는 자유 입력이 아니라 **관리되는 태그 사전**에서 선택한다. 자유 태그는 추천 피처로 쓸 수 없다. 태그 사전의 추가·병합은 admin(운영 API)에서 관리한다.
3. **취향의 명시적 신호**: 스크랩(강한 신호)과 필터 선택(명시적 요구)을 유저별로 조회 가능하게 유지한다.
4. **추천 도입 순서**: 규칙 기반(같은 태그·같은 상권·스크랩 유사도) → 지표로 효과 검증 → 그 후에만 ML/임베딩 검토. 처음부터 ML을 만들지 않는다.

## 8. 디자인 방향

- **컨셉**: Neon-Minimalism & Glassmorphism. 딥 다크 또는 클린 화이트 베이스 + 애시드 그린/일렉트릭 핑크 포인트.
- **타이포**: Pretendard. 타이틀은 화면을 압도하는 굵고 큰 폰트.
- **UX 원칙 (Zero-Friction)**: 햄버거 메뉴 금지, 하단 탭바 + 제스처 중심. 스크랩 등 핵심 액션에 마이크로 인터랙션(파티클, 햅틱).
- 세부 연출 레퍼런스는 legacy advanced_design 참고 (구현 여부·방식은 성능 규칙 PERF 우선).

## 9. 측정 지표 (초기)

- 활성화: 주간 신규 코스 수, 코스 생성 완료율(마법사 이탈률)
- 성장 루프: 코스 공유 클릭률, 공유 링크 유입 → 가입 전환율
- 콘텐츠 품질: 코스당 평균 스크랩, 신고율
- 글로벌: en 로케일 트래픽 비중

## 10. 커플 라이프사이클 정책

`Couple` 스키마와 코스 소유권 설계의 전제가 되는 확정 정책이다.

### 10.1. 연결 (Pairing)

- 한 유저가 **초대 링크/코드**를 생성해 상대에게 전달 → 상대가 **수락하면 성립**. 일방 연결 불가.
- 유저는 동시에 하나의 활성 커플에만 속한다.
- 연결 시 커플명(예: "지훈❤️민지")과 D-Day를 설정한다.

### 10.2. 솔로 유저 [확정: 솔로도 코스 생성 가능]

- 가입 즉시 코스 생성 가능 — "OO의 코스"로 표기.
- 커플 연결 시 본인 솔로 코스를 **커플명 코스로 업그레이드할지 선택**할 수 있다 (자동 전환 아님 — 상대와 무관한 과거 코스가 커플 이름을 달게 되는 문제 방지).
- 열람·스크랩·팔로우는 커플 여부와 무관하게 가능 (관광객 등 비커플 유저 수용).
- 명예의 전당은 커플 코스·솔로 코스를 구분 없이 스크랩 기준으로 다루되, "커플 코스" 뱃지로 시각 구분한다.

### 10.3. 해제 (이별) [확정: 유지 + 익명화]

- 어느 한쪽의 해제 요청으로 즉시 해제된다 (상대 동의 불요 — 잡아두는 UX는 CS 리스크).
- 공동 코스 처리:
  - 코스·꿀팁·사진은 **공개 유지** (플랫폼 콘텐츠 자산 보존)
  - 커플명은 **"익명 커플 코스"로 자동 전환** — 실명·닉네임 노출 즉시 제거
  - **명예의 전당에서 제외** (이별 커플의 전시 방지)
  - 당사자 누구든 개별 코스의 **삭제(비공개) 요청 가능** — 즉시 처리, 복구 불가 고지
- 해제된 커플의 D-Day·커플 프로필은 비활성화한다.

### 10.4. 재연결·신규 연결

- 해제 후 다른 상대와 연결하면 **새로운 Couple 엔티티**를 생성한다 (과거 커플의 이력·코스와 절대 병합하지 않음).
- 과거 커플의 익명화 코스는 새 커플과 무관하게 익명 상태를 유지한다.
- 같은 상대와 재결합 시에도 새 Couple로 시작한다 (이력 복원은 지원하지 않음 — 복잡도 대비 가치 없음).

### 10.5. 회원 탈퇴 연동

- 탈퇴 유저의 개인정보는 삭제하되, 코스 처리는 10.3과 동일한 익명화 규칙을 따른다 (커플 상대가 남아 있는 경우 상대의 콘텐츠 접근권 보존).
- 스키마 영향: `Course`의 소유권은 "당시의 Couple"을 참조하고, Couple은 상태(`ACTIVE | DISSOLVED`)를 가진다. 표시명은 코스 조회 시점의 커플 상태에 따라 동적으로 결정한다 (가이드 INT 원칙과 연동 — 이름을 코스에 복사 저장하지 않는다).
